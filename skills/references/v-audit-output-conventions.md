# v-audit output conventions

_Last reviewed: 2026-08-02 (single-source-of-truth fix: this file asserted v-audit-seo uses the `[DIM]-[NN]` format via `findings-id-convention.md`, but that skill actually emits a distinct `{PREFIX}{NNN}` scheme — carved out as an explicit exception, not a `[DIM]-[NN]` consumer; prior: 2026-07-05 ecosystem review sweep)._

> **Persona for this reference:** senior audit-tooling engineer
> responsible for cross-skill output compatibility. Loaded
> on-demand by every v-audit-* skill before emitting a report.
> The conventions here align audit outputs with v-ui-audit v3.8.5
> patterns (v-ui-audit was retired 2026-07-06, absorbed into
> `/v-audit-code`'s deep UX/a11y mode) so operators can diff across
> runs and across skill versions consistently.

Three conventions govern audit outputs: a version stamp on every
methodology block, a citation format that works in plain text and
clickable Markdown viewers, and a stable finding-ID scheme that
makes re-run diffs deterministic. None of these are negotiable —
they're the contract every audit skill speaks.

---

## Version stamp (REQUIRED)

The audit's methodology block / methodology section MUST emit a
line of the form:

```
Generated by {skill-name} v1.0
```

Where `{skill-name}` is this skill's name (e.g., `v-audit-seo`).
The version starts at v1.0 for skills adopting this convention;
bump the patch when behavior changes (re-runs of a different
patch version may produce non-comparable counts, which the diff
tooling needs to know).

**Why:** when an operator re-runs an audit and counts shifted,
the version stamp tells them whether the count change reflects a
real project change or a methodology change. Without the stamp,
every re-run is ambiguous.

---

## File:line citation format (PREFERRED)

Use the clickable Markdown link form for file:line citations:

```
[resources/js/Pages/Pricing.tsx:67](resources/js/Pages/Pricing.tsx#L67)
```

This renders as plain text in non-Markdown viewers AND as a
clickable link in GitHub / VS Code preview / Cowork chat.
Multi-line spans use `#L67-L70`. Plain `path:line` (without the
link wrapper) remains accepted as fallback.

The clickable form is preferred but not enforced — Gate 1 only
requires the citation to be parseable. Use clickable form on
every finding when feasible; fall back to plain on edge cases
(synthetic paths, generated files).

**Why:** clickable links cut review time roughly in half on long
audits. The fallback exists because some citation paths
(synthetic test fixtures, ephemeral build artifacts) don't
benefit from linkification.

## Findings ID convention (RECOMMENDED for re-runs)

**Precedence:** skills with a registered dimension-prefix table
in `findings-id-convention.md` using the `[DIM]-[NN]` format
(v-audit-messaging, v-audit-sales-pricing, v-audit-growth,
v-audit-analytics, v-audit-admin, v-anti-template-gauntlet) use
that format instead — see that file for the tombstoned v-ui-audit
table, retired 2026-07-06 into `/v-audit-code`. **v-audit-seo is a
registered exception, NOT a `[DIM]-[NN]` consumer** — it emits its
own `{PREFIX}{NNN}` scheme (no separator, e.g. `T001`, `SD001`) —
canonical per `v-audit-seo/SKILL.md` § Output conventions, and
registered as an exception row in `findings-id-convention.md` § v-audit-seo.
The `D{dim}` format below is the fallback ONLY for skills without a
registered prefix table — never mix any of the three schemes in
one report.

Stable IDs let operators diff audits deterministically across
re-runs. Fallback format: `D{dim}-{C|F|P|A}-{nnn}` where:

- `D{dim}` = dim number
- middle letter = category: `C` Correctness, `F` Craft, `P`
  Pixel-perfect, `A` AI-tells
- `{nnn}` = sequential within bucket, zero-padded

When a finding persists across re-runs, keep the same ID. New
findings get fresh IDs. Resolved findings vacate their IDs
(don't recycle within a quarter — keeps diffs unambiguous).

First-audit runs MAY skip IDs (no diff target exists yet). Once
adopted, the IDs are kept stable across re-runs of the same skill
version.

**Why:** without stable IDs, every re-run looks like a fresh
audit. Operators can't tell which findings persisted, which were
fixed, and which are new — eroding the value of running audits
repeatedly.

## After the audit (REQUIRED next-step line)

Every audit skill's operator-facing summary must end with a pointer to consolidation, so an operator who ran a
specialist DIRECTLY (not via `/v-audit-orchestrator`, which auto-consolidates) still knows the next step:

> **Next step:** If you've run other `/v-audit-*` skills on this project recently, run `/v-audit-consolidate`
> to merge overlapping findings into one prioritized, de-duplicated backlog before implementing.

This closes the discoverability gap where a specialist's output named its own pack dir but never told the
operator that consolidation across audits is the intended sequencing step (audits → consolidate → build).

## Behavior contract

These conventions are uniform across every audit skill that loads
this reference. When a convention changes (e.g., a new clickable
link syntax), update this file once — every skill picks up the
change without further edits.

When adopting these conventions in a new audit skill, the
skill's body should contain a concise pointer block referencing
this file (typically 15–20 lines covering Moved-to / Summary /
Trigger to load / Behavior unchanged), not a copy of the
conventions inline. The skill's methodology block must emit the
version stamp on every run; that emission is the only inline
obligation.
